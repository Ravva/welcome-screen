# PRD / ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ТЗ)

**Наименование системы:** Модуль автоматического распознавания лиц и вывода приветствий «Welcome Screen»  
**Платформа развертывания:** Ubuntu Server (Docker-контур)  

---

## 1. Назначение и цели системы
Система предназначена для автоматической фиксации посетителей/сотрудников на входе в здание с помощью IP-камеры, распознавания их лиц на локальном сервере и мгновенного отображения персонального приветствия (карточки сотрудника) на информационном экране (телевизоре).

**Цели проекта:**
* Автоматизация учета посещаемости/прибытия сотрудников.
* Повышение лояльности и технологического имиджа компании.
* Обеспечение высокой скорости отклика системы (целевое значение — до 1.2 секунды от появления в кадре до вывода на экран).

### 1.1. Scope / MVP
В первую версию системы входит:
* одна IP-камера в зоне узкого прохода/рамки металлоискателя;
* один ТВ-экран для отображения режима ожидания и приветствий;
* локальное распознавание сотрудников и посетителей без отправки биометрических данных во внешние облака;
* отображение персонального приветствия для распознанного сотрудника;
* отображение нейтрального приветствия для неизвестного лица;
* сохранение и логирование событий распознавания;
* сохранение фото неизвестных лиц;
* базовая панель администратора;
* управление сотрудниками, эталонными фотографиями и журналом посещений;
* настройка similarity-порога, ROI и anti-flood-таймаута;
* WebSocket-доставка событий на ТВ;
* защищенный локальный доступ через Nginx, HTTPS и WSS с самоподписанными сертификатами;
* простая страница состояния `/health`.

### 1.2. Не входит в MVP / Non-goals
В первую версию не входят, если не будет принято отдельное решение:
* мобильное приложение;
* интеграция со СКУД;
* учет рабочего времени как юридически значимая система;
* распознавание эмоций;
* определение пола/возраста;
* облачная аналитика;
* поддержка нескольких камер;
* поддержка нескольких ТВ-экранов;
* сложная BI-аналитика;
* полноценная система мониторинга на базе Prometheus/Grafana;
* автоматическая юридическая обработка согласий на биометрию.

### 1.3. Пользовательские истории
* Как администратор, я хочу добавлять сотрудников и загружать их эталонные фотографии, чтобы система могла распознавать их на входе.
* Как администратор, я хочу настраивать similarity-порог, ROI и anti-flood-таймаут, чтобы адаптировать систему под реальные условия проходной.
* Как сотрудник, я хочу видеть персональное приветствие на экране, когда прохожу через входную зону.
* Как менеджер/оператор, я хочу просматривать журнал событий, чтобы видеть, кто и когда был распознан системой.
* Как администратор, я хочу видеть события неизвестных лиц и сохраненные снимки, чтобы анализировать незарегистрированные посещения.
* Как технический специалист, я хочу видеть страницу `/health`, чтобы быстро проверить состояние сервисов.

## 2. Архитектура и технические требования к серверу

### 2.1. Аппаратная конфигурация (Целевой сервер)
* **ОС:** Ubuntu Server (версия LTS 22.04 или 24.04)
* **Процессор (CPU):** 56 vCPU (архитектура x86_64)
* **Оперативная память (RAM):** 64 ГБ
* **Графический ускоритель (GPU):** Отсутствует (вычисления полностью на CPU)
* **Сеть:** Локальная сеть 1 Гбит/с (минимальные задержки между камерой, сервером и ТВ)

### 2.2. Программный стек (Docker-контур)
Вся серверная часть должна быть контейнеризирована с помощью `docker-compose`. Стек должен включать:
1. **Контейнер распознавания (Face Recognition):** Open-source решение **CompreFace** (базируется на моделях InsightFace). Настройки контейнера должны быть принудительно оптимизированы для многопоточности на CPU (`NUM_THREADS` настроен на утилизацию до 48-52 ядер).
2. **Контейнер видеоаналитики (Stream Handler):** Скрипт/сервис на Python (OpenCV / PyAV) для захвата RTSP-потока.
3. **Контейнер бэкенда (Application Backend):** Node.js (NestJS/Fastify) ИЛИ Python (FastAPI). Отвечает за бизнес-логику, связь с БД и управление WebSocket-соединениями.
4. **Контейнер СУБД:** PostgreSQL (хранение логов, профилей сотрудников) или интеграция с существующей CRM/ERP заказчика.

### 2.3. Целевая архитектура взаимодействия компонентов
Система состоит из следующих сервисов:
1. `camera-stream-handler` — получает RTSP-поток, применяет ROI, сэмплирует кадры и передает изображения на распознавание.
2. `compreface` — выполняет детекцию и идентификацию лиц.
3. `backend-api` — хранит бизнес-данные, управляет сотрудниками, применяет anti-flood, записывает события и рассылает WebSocket-уведомления.
4. `postgres` — хранит профили сотрудников, настройки, пользователей и логи посещений.
5. `tv-frontend` — отображает режим ожидания и карточки приветствия.
6. `admin-frontend` — предоставляет интерфейс управления сотрудниками и журналом посещений.
7. `reverse-proxy` — обеспечивает HTTPS/WSS и маршрутизацию запросов внутри локального контура.

Backend должен выступать центральным координатором бизнес-логики: хранить сотрудников, управлять связью с CompreFace, применять anti-flood, записывать логи и отправлять события на ТВ.

Базовый поток обработки:
```text
IP Camera → Stream Handler → CompreFace → Backend → WebSocket → TV Frontend
```

Альтернативный поток:
```text
IP Camera → Stream Handler → Backend → CompreFace → Backend → WebSocket → TV Frontend
```

Окончательный вариант интеграции Stream Handler, Backend и CompreFace должен быть подтвержден тестированием задержек и стабильности на целевом сервере.

## 3. Функциональные требования

### 3.0. Основные пользовательские сценарии

#### Сценарий 1: Распознанный сотрудник входит в здание
1. IP-камера фиксирует лицо человека в зоне прохода.
2. Stream Handler получает кадр из RTSP-потока, применяет ROI и сэмплирование кадров.
3. Кадр или вырезанная область лица передается в подсистему распознавания.
4. CompreFace выполняет идентификацию лица по базе сотрудников.
5. Backend получает результат распознавания, проверяет anti-flood-ограничения и записывает событие в журнал.
6. Backend отправляет событие приветствия на ТВ-фронтенд через WebSocket.
7. ТВ-экран отображает персональную карточку сотрудника 5–7 секунд и возвращается в режим ожидания.

#### Сценарий 2: Неизвестное лицо
1. Камера фиксирует лицо человека, отсутствующего в базе сотрудников.
2. Система определяет лицо как неизвестное, если результат распознавания ниже настроенного порога similarity.
3. На ТВ-экране отображается нейтральное приветствие для незнакомца/гостя.
4. Событие обязательно логируется в журнал посещений со статусом `unknown`.
5. Фото неизвестного лица сохраняется для последующего анализа администратором.
6. Опционально система может отправлять уведомление администратору о появлении неизвестного лица. Канал уведомлений и условия отправки будут уточнены отдельно.

#### Сценарий 3: Несколько лиц в кадре
Проект рассчитан на эксплуатацию в узком проходе — в зоне рамки металлоискателя на входе в здание, где физически может проходить только один человек за раз. Поэтому базовый сценарий предусматривает строго одно лицо в кадре.

Если в кадре обнаружено более одного лица, система должна зафиксировать событие в журнале как нестандартное (`multiple_faces`) и не выполнять персональное приветствие до уточнения бизнес-логики обработки таких случаев.

### 3.1. Подсистема захвата и предобработки видеопотока (Stream Handler)
* Подключение к IP-камере по протоколу **RTSP**.
* В рамках MVP поддерживается **одна IP-камера**, установленная в зоне узкого прохода/рамки металлоискателя.
* Декодирование потока и оптимизация нагрузки на CPU:
    * Анализ не каждого кадра, а сэмплирование (например, каждый 5-й кадр / 5-10 fps).
    * Программное ограничение зоны детекции (ROI — Region of Interest), чтобы исключить обработку прохожих на заднем плане.
    * Сжатие кадра до разрешения не более 1280x720 перед отправкой на распознавание.
* Передача вырезанного кадра (или координат лица) во внутренний API CompreFace.

#### 3.1.1. Требования к IP-камере
* Поддержка RTSP-потока.
* Рекомендуемое разрешение: не ниже 1920x1080.
* Частота кадров: не ниже 25 fps на исходном потоке камеры.
* Кодек: H.264 предпочтительно; H.265 допускается при подтверждении совместимости с обработчиком потока.
* Наличие WDR или аналогичной функции компенсации сложного освещения желательно.
* Камера должна быть установлена таким образом, чтобы лицо проходящего человека находилось в ROI и имело достаточный размер в кадре.
* Рекомендуемая высота установки: 1.6–2.2 м, точное расположение определяется при обследовании места установки.
* Камера должна иметь статический IP-адрес или зарезервированный адрес в DHCP.
* Доступ к RTSP-потоку должен быть защищен логином и паролем.
* RTSP-задержка камеры должна быть минимальной и подлежит проверке при пусконаладке.

### 3.2. Подсистема распознавания (Face ID Core)
* Идентификация лица по предварительно обученной базе векторов (эмбеддингов).
* Настраиваемый порог уверенности (по умолчанию `Similarity >= 0.82`).
* Фильтрация повторных срабатываний: предотвращение «спама» уведомлениями, если человек стоит перед камерой. Anti-flood: не более одного приветствия для одного ID в течение 60 секунд по умолчанию.
* Anti-flood применяется для единственной камеры, предусмотренной MVP.
* Anti-flood-таймаут должен настраиваться в панели администратора.
* Все события распознавания должны логироваться, включая повторные срабатывания, неизвестные лица и нестандартные случаи.
* Базовый сценарий предусматривает строго одно лицо в кадре.
* Требования к условиям распознавания:
    * расстояние до камеры: ориентировочно 1–3 м, точные значения уточняются при установке;
    * угол поворота лица: желательно не более 30° относительно камеры;
    * лицо должно быть достаточно освещено и не должно быть полностью перекрыто посторонними предметами;
    * минимальный размер лица в кадре должен быть достаточным для устойчивого распознавания и проверяется на этапе калибровки;
    * эталонные фотографии сотрудников должны быть в анфас, без головных уборов и темных очков.
* Требования к точности и производительности распознавания должны быть подтверждены тестированием на реальной точке установки.

#### 3.2.1. Нагрузочное и калибровочное тестирование распознавания
Перед промышленной эксплуатацией проводится тестирование:
* 1 камера, 5–10 fps анализа после сэмплирования.
* Строго одно лицо в кадре в штатном сценарии.
* Проверка на базе сотрудников разного размера: ориентировочно 100 / 500 / 1000 профилей при необходимости.
* Проверка времени ответа recognition API.
* Проверка стабильности similarity-порога.
* Проверка влияния освещения, положения лица и расстояния до камеры.
* Целевые метрики точности и допустимые уровни ложных срабатываний/пропусков фиксируются по итогам тестов и калибровки.

### 3.3. Подсистема вывода информации (Фронтенд для ТВ)
* Разработка веб-страницы (SPA на React/Vue/Vanilla JS), адаптированной под разрешение телевизора (обычно 1920x1080 Full HD или 4K).
* Подключение к бэкенду по протоколу **WebSockets** для обеспечения Real-time доставки событий.
* **Режимы работы экрана:**
    * *Режим ожидания:* Корпоративный скринсейвер, видео, текущее время и погода.
    * *Режим приветствия:* При получении события по WS — плавное появление карточки (анимация fadeIn за 300мс). Карточка содержит: ФИО, должность, отдел, фото сотрудника и текст приветствия. Время отображения: 5–7 секунд, после чего карточка плавно исчезает.

### 3.4. Панель администрирования (Web-интерфейс менеджера)
* Интерфейс для управления базой сотрудников: добавление, удаление, редактирование ФИО и должностей.
* Возможность загрузки эталонных фотографий сотрудников (от 1 до 3 фото на человека в анфас, без головных уборов и очков).
* Просмотр лога посещений (Имя, Время, Статус распознавания).
* Управление сотрудниками:
    * создание сотрудника;
    * редактирование ФИО, должности, отдела и других карточных данных;
    * деактивация сотрудника без физического удаления данных;
    * удаление сотрудника при наличии соответствующих прав;
    * поиск и фильтрация сотрудников;
    * импорт сотрудников из CSV/Excel — опционально, решение уточняется отдельно;
    * загрузка нескольких эталонных фото;
    * проверка качества загружаемых фото при технической возможности;
    * повторная индексация/обновление профиля лица в CompreFace.
* Работа с логами:
    * фильтр по дате и времени;
    * фильтр по сотруднику;
    * фильтр по статусу события (`recognized`, `unknown`, `multiple_faces`, `duplicate`, `error`);
    * просмотр similarity;
    * просмотр камеры — для MVP значение будет соответствовать единственной камере;
    * просмотр сохраненного снимка события, если снимок был сохранен;
    * экспорт логов в CSV/XLSX — опционально, решение уточняется отдельно.
* Роли пользователей:
    * администратор;
    * менеджер/оператор;
    * пользователь только для просмотра логов.

### 3.5. Очередь и правила отображения приветствий на ТВ
* В штатном сценарии в зоне прохода находится один человек, однако события могут приходить быстрее, чем завершается показ текущей карточки.
* Если во время показа карточки приходит новое событие, оно должно помещаться в очередь отображения.
* Рекомендуемая максимальная длина очереди — 5 событий.
* При переполнении очереди возможны стратегии FIFO или `latest wins`; окончательное решение будет принято позднее.
* Для одного и того же сотрудника повторные приветствия ограничиваются anti-flood-таймаутом.
* События неизвестных лиц также должны отображаться в соответствии с правилами очереди, если не отключены администратором.

## 4. Требования к надежности, безопасности и производительности

### 4.1. Безопасность
* Доступ к веб-панели администратора и бэкенду должен быть защищен авторизацией (JWT / сессии).
* Локальный контур: все биометрические векторы и фотографии хранятся строго внутри сервера на Ubuntu, без отправки во внешние облачные сервисы.
* Работа фронтенда ТВ с бэкендом должна происходить по защищенным протоколам (HTTPS / WSS) внутри локальной сети.
* RTSP-логины, пароли БД, JWT-secret, учетные данные администратора и иные секреты не должны храниться в исходном коде или напрямую в `docker-compose.yml`.
* Для хранения секретов должны использоваться `.env`-файлы, переменные окружения или Docker secrets, в зависимости от выбранного способа развертывания.
* Доступ к `.env`-файлам и конфигурации с секретами должен быть ограничен на уровне файловой системы сервера.

#### 4.1.1. Nginx, HTTPS и WSS
В качестве reverse proxy используется **Nginx**.

Nginx должен выполнять следующие функции:
* принимать входящие HTTPS-запросы внутри локальной сети;
* маршрутизировать запросы к backend API;
* обслуживать или проксировать фронтенд ТВ;
* обслуживать или проксировать админ-панель;
* проксировать WebSocket-соединения для ТВ-фронтенда;
* выполнять редирект HTTP → HTTPS, если HTTP-порт открыт;
* ограничивать доступ к внутренним сервисам, чтобы CompreFace, PostgreSQL и служебные API не были доступны напрямую из локальной сети без необходимости.

Сертификаты:
* используются самоподписанные TLS-сертификаты;
* сертификат должен генерироваться для локального доменного имени или IP-адреса сервера;
* корневой сертификат или сам сертификат должен быть установлен как доверенный на ТВ/браузере администратора, если требуется убрать предупреждение браузера;
* срок действия сертификата и порядок его ротации должны быть описаны в инструкции администратора.

Рекомендуемые настройки Nginx:
* включить TLS 1.2/1.3;
* отключить устаревшие протоколы SSL/TLS;
* настроить `proxy_read_timeout` для WebSocket-соединений;
* передавать заголовки `Upgrade` и `Connection` для WebSocket;
* передавать `X-Forwarded-For`, `X-Forwarded-Proto`, `Host`;
* ограничить размер загружаемых файлов для фото сотрудников на уровне Nginx и backend;
* включить access/error logs;
* не публиковать наружу порты PostgreSQL и внутренних сервисов, если это не требуется.

Примерный фрагмент конфигурации WebSocket-проксирования:
```nginx
location /ws/ {
    proxy_pass http://backend-api:3000/ws/;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 3600s;
}
```

Примерный фрагмент HTTPS-настроек:
```nginx
server {
    listen 443 ssl http2;
    server_name welcome-screen.local;

    ssl_certificate /etc/nginx/certs/welcome-screen.crt;
    ssl_certificate_key /etc/nginx/certs/welcome-screen.key;
    ssl_protocols TLSv1.2 TLSv1.3;

    location /api/ {
        proxy_pass http://backend-api:3000/api/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

#### 4.1.2. Роли и права доступа
Система должна поддерживать роли пользователей:
* `admin` — полный доступ к настройкам, сотрудникам, логам, пользователям и техническим параметрам;
* `manager` / `operator` — управление сотрудниками и просмотр логов без доступа к критическим системным настройкам;
* `viewer` — только просмотр логов и состояния системы.

Права доступа должны проверяться на backend, а не только на frontend.

#### 4.1.3. Аудит действий администратора
Система должна вести аудит значимых действий пользователей админ-панели:
* вход в систему;
* неуспешная попытка входа;
* создание, изменение, деактивация и удаление сотрудника;
* загрузка и удаление эталонных фотографий;
* изменение similarity-порога;
* изменение ROI;
* изменение anti-flood-таймаута;
* изменение ролей пользователей;
* экспорт логов;
* изменение настроек камеры;
* перезапуск/перекалибровка распознавания, если такая функция будет доступна из админки.

Запись аудита должна содержать:
* идентификатор пользователя;
* действие;
* объект действия;
* дату и время;
* IP-адрес клиента;
* результат действия: успех/ошибка.

#### 4.1.4. Юридические и биометрические данные
Система обрабатывает фотографии лиц и биометрические признаки. Юридические требования к согласию сотрудников, срокам хранения, регламенту удаления и доступу к биометрическим данным должны быть согласованы отдельно до промышленной эксплуатации.

### 4.2. Производительность (SLA)
* Время сквозной обработки (от прохода человека перед камерой до вывода карточки на ТВ) не должно превышать **1.2 секунды**.
* Сервер должен выдерживать параллельный разбор потока в пиковые часы (утро/вечер), задействуя векторные инструкции CPU (AVX2/AVX-512), встроенные в сборку CompreFace.

SLA должен оцениваться по 95-му перцентилю: не менее 95% штатных событий распознавания должны приводить к отображению карточки на ТВ не позднее 1.2 секунды после появления лица в ROI.

Рекомендуемая декомпозиция задержки:

| Этап | Целевое время |
|---|---:|
| Захват кадра из RTSP | ≤ 100 мс |
| Предобработка / ROI | ≤ 50 мс |
| Передача в CompreFace | ≤ 50 мс |
| Распознавание | ≤ 500 мс |
| Backend logic + anti-flood + запись события | ≤ 100 мс |
| WebSocket-доставка | ≤ 50 мс |
| Отрисовка и анимация на ТВ | ≤ 300 мс |
| Итого | ≤ 1.2 сек |

Для измерения SLA рекомендуется проставлять timestamp на ключевых этапах обработки события:
* получение кадра обработчиком потока;
* отправка на распознавание;
* получение результата распознавания;
* запись события backend;
* отправка события по WebSocket;
* получение события ТВ-фронтендом;
* начало отображения карточки.

### 4.3. Надежность, healthcheck и эксплуатационная диагностика
Система должна предоставлять простую страницу состояния `/health`.

Endpoint `/health` должен быть доступен через backend и Nginx и возвращать состояние ключевых компонентов:
* backend API;
* PostgreSQL;
* CompreFace API;
* Stream Handler;
* RTSP-подключение к камере;
* WebSocket-сервер;
* доступность директории хранения фотографий/снимков;
* версия приложения и время последнего запуска.

Пример ответа `/health`:
```json
{
  "status": "ok",
  "version": "1.0.0",
  "startedAt": "2026-01-01T08:00:00Z",
  "services": {
    "postgres": "ok",
    "compreface": "ok",
    "streamHandler": "ok",
    "rtspCamera": "ok",
    "websocket": "ok",
    "storage": "ok"
  }
}
```

Если один из компонентов недоступен, `/health` должен возвращать статус `degraded` или `error` и описание проблемного компонента.

Контейнеры должны иметь Docker healthcheck, если это технически возможно.

### 4.4. Логирование
Система должна вести технические логи:
* запуск и остановка сервисов;
* ошибки подключения к RTSP;
* ошибки CompreFace API;
* ошибки backend API;
* ошибки WebSocket-соединений;
* ошибки загрузки и обработки фотографий;
* события превышения SLA;
* события нестандартного поведения: `unknown`, `multiple_faces`, `duplicate`, `error`.

Логи должны быть доступны на сервере через стандартные механизмы Docker/log-файлов. Подключение полноценной системы мониторинга не входит в MVP.

## 5. Критерии приёмки

### 5.1. Распознавание
* Система распознаёт сотрудников из тестовой базы при штатном проходе через рамку металлоискателя.
* Similarity-порог настраивается администратором.
* Неизвестное лицо получает статус `unknown`.
* Для неизвестного лица отображается нейтральное приветствие.
* Фото неизвестного лица сохраняется.
* Все события распознавания логируются.
* Повторное приветствие одного и того же сотрудника ограничивается anti-flood-таймаутом.
* Anti-flood-таймаут настраивается в админке.

### 5.2. ТВ-фронтенд
* ТВ-фронтенд открывается в браузере телевизора/устройства вывода.
* Экран подключается к backend по WSS через Nginx.
* В режиме ожидания отображается корпоративный скринсейвер, время и/или другой согласованный контент.
* При событии `recognized` отображается карточка сотрудника.
* Карточка содержит ФИО, должность, отдел, фото и приветственный текст.
* При событии `unknown` отображается нейтральное приветствие.
* Карточка отображается 5–7 секунд и плавно исчезает.
* При потере WebSocket-соединения фронтенд пытается переподключиться.

### 5.3. Админ-панель
* Доступ к админ-панели защищен авторизацией.
* Реализованы роли `admin`, `manager/operator`, `viewer`.
* Можно создать, отредактировать, деактивировать и удалить сотрудника при наличии прав.
* Можно загрузить 1–3 эталонные фотографии сотрудника.
* Можно просмотреть журнал посещений.
* Можно фильтровать журнал по дате, сотруднику и статусу.
* Можно просмотреть similarity и снимок события, если он сохранен.
* Действия администратора фиксируются в audit log.

### 5.4. Безопасность
* Система работает через Nginx по HTTPS/WSS с самоподписанным сертификатом.
* Backend API и WebSocket доступны только через согласованные маршруты Nginx.
* PostgreSQL и внутренние сервисы не опубликованы наружу без необходимости.
* Секреты не хранятся в исходном коде и не коммитятся в репозиторий.
* RTSP-доступ к камере защищен логином и паролем.

### 5.5. Производительность и стабильность
* Не менее 95% штатных событий отображаются на ТВ не позднее 1.2 секунды после появления лица в ROI.
* Система стабильно работает не менее 8 часов в тестовом режиме без ручного перезапуска.
* `/health` корректно показывает состояние основных компонентов.
* При недоступности камеры или CompreFace система фиксирует ошибку в логах и отображает degraded/error-статус в `/health`.

### 5.6. Комплект поставки
* Исходный код всех разработанных компонентов.
* `docker-compose.yml` и связанные конфигурационные файлы.
* Конфигурация Nginx.
* Инструкция по генерации/замене самоподписанных сертификатов.
* Инструкция по первичному запуску.
* Инструкция администратора.
* Описание резервного копирования и восстановления — если будет согласовано отдельно.

## 6. Этапы разработки и приёмки

1. **Этап 1: Проектирование и развертывание инфраструктуры.** Настройка Ubuntu, Docker, установка CompreFace, проверка утилизации ядер CPU.
2. **Этап 2: Разработка бэкенда и обработчика видео.** Написание скрипта захвата RTSP, интеграция с API распознавания, создание WebSocket-сервера.
3. **Этап 3: Разработка фронтенда (Интерфейс ТВ) и Админки.** Верстка экранов, интеграция анимаций, логика работы WebSocket-клиента.
4. **Этап 4: Тестирование и калибровка.** Настройка оптимального порога `similarity`, тестирование anti-flood фильтра.
5. **Этап 5: Сдача проекта.** Передача исходного кода, `docker-compose.yml` файлов и инструкций по администрированию.

## 7. Основные риски проекта

### 7.1. Производительность CPU-only распознавания
Система должна работать без GPU. Несмотря на наличие 56 vCPU, фактическая производительность зависит от модели CPU, виртуализации, AVX2/AVX-512, настроек CompreFace и размера базы сотрудников.

Меры снижения риска:
* обязательное нагрузочное тестирование на целевом сервере;
* сэмплирование кадров до 5–10 fps;
* ограничение ROI;
* проверка времени ответа CompreFace;
* настройка числа потоков CompreFace;
* фиксация фактических SLA-метрик после калибровки.

### 7.2. Качество камеры и освещения
Точность распознавания существенно зависит от установки камеры, освещения, угла лица и размера лица в кадре.

Меры снижения риска:
* обследование места установки;
* тестирование RTSP-задержки;
* настройка ROI;
* проверка камеры при дневном и искусственном освещении;
* использование камеры с WDR;
* калибровка similarity-порога на реальных проходах.

### 7.3. Биометрические и персональные данные
Система хранит фотографии и биометрические признаки. Юридические требования к согласию, хранению и удалению данных должны быть определены отдельно.

Меры снижения риска:
* локальное хранение данных без облачных сервисов;
* разграничение ролей доступа;
* аудит действий администраторов;
* ограничение доступа к серверу и файлам;
* отдельное согласование регламента хранения и удаления данных.

### 7.4. Неизвестные лица
Система сохраняет фото неизвестных лиц и может уведомлять администратора. Нужно дополнительно определить срок хранения таких снимков и правила доступа к ним.

Меры снижения риска:
* логирование статуса `unknown`;
* ограничение доступа к снимкам;
* отдельное согласование срока хранения;
* возможность отключения показа или уведомлений для неизвестных лиц при необходимости.

### 7.5. Нестандартная ситуация с несколькими лицами
Штатная зона установки физически рассчитана на одного человека. Тем не менее алгоритм может обнаружить несколько лиц из-за отражений, фона или нарушений сценария прохода.

Меры снижения риска:
* логировать событие как `multiple_faces`;
* не показывать персональное приветствие до уточнения логики;
* использовать ROI для исключения заднего плана;
* тестировать на реальной точке установки.

### 7.6. Зависимость от CompreFace
CompreFace является ключевой open-source зависимостью.

Меры снижения риска:
* проверить актуальность Docker-образов;
* проверить API на целевых сценариях;
* проверить лицензионные условия;
* описать процедуру резервного копирования данных CompreFace;
* изолировать бизнес-логику в backend, чтобы снизить связанность с конкретным recognition-сервисом.

## 8. Актуализированные рекомендации по реализации

1. Сохранить документ под текущим именем `PRD.md`, но считать его комбинированным PRD/ТЗ-документом: он содержит как продуктовые, так и технические требования.
2. Backend должен быть центральным координатором бизнес-логики: сотрудники, роли, anti-flood, аудит, логи, события WebSocket, связь с CompreFace.
3. Stream Handler должен быть максимально специализированным: RTSP, ROI, сэмплирование, подготовка кадров и передача на распознавание/в backend.
4. Nginx использовать как единую точку входа для HTTPS/WSS внутри локальной сети.
5. Самоподписанный сертификат нужно включить в комплект поставки вместе с инструкцией по генерации, установке доверия и ротации.
6. В MVP не публиковать напрямую PostgreSQL, CompreFace и внутренние порты сервисов в локальную сеть без необходимости.
7. Все секреты хранить вне исходного кода: `.env`, переменные окружения или Docker secrets.
8. Для ТВ-фронтенда предусмотреть автоматическое переподключение к WebSocket и визуальный статус соединения/ошибки в техническом режиме.
9. Реализовать `/health` как простой и достаточный механизм первичной диагностики вместо внедрения полноценного мониторинга на первом этапе.
10. До промышленного запуска обязательно провести калибровку similarity-порога, ROI и anti-flood-таймаута на реальной точке установки.
11. Для неизвестных лиц уже зафиксировано сохранение фото и логирование; срок хранения и правила удаления нужно согласовать отдельно.
12. Юридические вопросы по биометрии и персональным данным отложены, но должны быть закрыты до промышленной эксплуатации.
13. Стратегия переполнения очереди приветствий пока не финализирована; рекомендуется протестировать FIFO и `latest wins` на реальных сценариях прохода.
14. Для сдачи проекта подготовить отдельные инструкции: запуск, администрирование, замена сертификатов, резервное копирование, восстановление после сбоя и диагностика через `/health`.
